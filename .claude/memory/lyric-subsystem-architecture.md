Lyric documents (`src/lyric-list/`) are **not** ordinary slide documents. A
`LyricAppDocument` has no editable canvas: every slide's content is one
`type: 'html'` canvas item whose HTML is generated by the **`open-lyric`**
dependency, then dropped into a normal `Slide`.

Pipeline: `Lyric` (file) → `initOpenLyric()` builds an `OpenLyric` instance →
`LyricAppDocumentStage{0,1}.getElementMap(options)` → `Record<sectionKey, html>`
→ `genSlide()` wraps each in a `LyricSlide`. `getValue()` produces the extra
"whole song" info slide.

Things that bite:

- **`LyricAppDocument.openLyric` is a public mutable field assigned from exactly
  one React component** (`LyricSlidesPreviewerComp`). Any renderer where that
  component has not mounted — the `screen.html` window, a stage instance built
  on demand by `lyricSlideScreenHelpers` — sees `null`. Never make slide output
  depend on it being set; read the persisted setting instead
  (`getOpenLyricFontSetting()` in `lyricHelpers.ts`). This caused the projected
  lyric to render at open-lyric's 16px default while the operator's previewer
  showed the configured 61px.
- **`getOpenLyricPreviewer()` returns the SHARED instance when one is live**
  (`liveOpenLyric`: the HELD one first, then the document's own field) and only
  falls back to `initOpenLyric` (history-head read + JSON.parse + full
  open-lyric re-parse) on a cold miss. Do NOT re-read from disk here — it sits
  on the per-slide path (`getSlidesQuick` calls it per render per stage pane).
  The owner keeps it current on the file's `update` event
  (`LyricManager.refreshOpenLyricContent`).
- **A song's slides are built BEFORE the click, like a PPTX's (2026-10-15).**
  Reported as _"lyric slides is slow at clicking, should do pre-caching like
  pptx slides"_. A card holds HTML for its PANE's stage, so a screen on another
  `St:` re-derived the slide at click time. A look-ahead stage rebuilt the
  whole deck. The First slide re-drew a whole-song PNG. The screen stage's
  document had no `OpenLyric`, so the song was re-read and re-parsed 2-3x per
  click, and the 10 s element-map cache was cold a minute later. A trace of
  one click to an `St: 2` screen under a stage-0 pane: 2.6 s of main-thread
  work, then 0.76 s.
  - `lyricWarmSlidesHelpers.ts` (a leaf) is the store: per file, the live
    `OpenLyric`s held and one deck per stage, under `genWarmDeckKey` (every
    option + file + stage + display size).
  - `useLyricWarmSlides`, mounted by `LyricSlidesPreviewerComp`, HOLDS the song
    in a LAYOUT effect. That way the panes' own first `getSlides()` (a passive
    effect lower down) is already stored.
  - It warms every screen's `St:` that no pane shows: one stage at a time,
    debounced per instance. It re-runs on a screen's `instance` event, when a
    pane is added or hidden, and after the `update` handler's `clearCache`.
  - `getSlides()` (no key) stores the deck; `getSlideById` reads it first. The
    look-ahead mixin's override does too.
  - Bounded by what is on screen, never by time: the last release deletes the
    entry. The decks must NOT live on the stage documents, which are cached
    for good.
  - `clearCache` drops every stage's decks and takes a new generation from ONE
    renderer-wide counter. A build reads the generation BEFORE it starts, so a
    deck rendered from text an edit replaced mid-build is refused, and so is
    one begun under a hold since released. A side effect: dev StrictMode's
    remount refuses a pane's first deck.
  - **The held `OpenLyric` beats the field.** A stage that was once a pane
    keeps its old previewer's instance for good, and with it the song as it
    stood then.
- **Stages are separate document instances, and there is no ceiling on the
  number (2026-09-27).** `getLyricAppDocumentStageByStage()` returns a different
  instance per stage, each with its own `openLyric` field and its own cache
  entries. `LYRIC_APP_DOCUMENT_STAGE_CLASSES` is the LAYOUT list, not the stage
  list: stage 0's `stageOpenLyricOptions.css` hides chords and section titles
  (`display: none`), stages 1–5 have their own entries (`Stage2`–`Stage5`
  since 2026-09-29), and a stage past the list falls back to
  `FALLBACK_STAGE_CLASS` = `LyricAppDocumentStage1` — deliberately NOT the last
  entry (`isWithKeyNote: true`, no hiding) — and differs only
  by its own `lyric-stage-style-<stage>` record. What makes that safe is
  `LyricAppDocumentStageAbstract.getStageInstance(filePath, stage)`: the
  instance cache keys on the CLASS NAME plus the path, so the stage goes in as
  `_getInstance`'s new `cacheKeySuffix` and is STAMPED on the new object.
  Without it a class IS the identity, which is why the resolver used to clamp at
  the last layout — and clamping handed stage 2, 3 and 4 the one stage-1
  instance while still echoing the asked-for number back, so a second pane was a
  byte-identical clone and a screen on `St: 3` showed the stage-1 render.
  Anything that renders per stage must key on the NUMBER, never on the class.
- **Each stage's style is a user setting now (2026-08-07).**
  `slidePaddingPercentage` / `slideBackgroundAlpha` / `extraSlideFontSize` /
  `slideTheme` used to be hard-coded `LyricAppDocument` fields nothing ever
  assigned. They are now one JSON blob per stage — `lyric-stage-style-<stage>` —
  read through `get stageStyle()` and edited from the ⚙ on each Stage Previewer
  chip. Three things to keep:
  - `src/lyric-list/lyricStageStyleHelpers.ts` is a **leaf** (only
    `../helper/settingHelpers`) precisely so `LyricAppDocument` can import it
    without closing the `lyricHelpers → Stage0 → StageAbstract → LyricAppDocument`
    cycle. `LyricAppDocumentStageAbstract` must NOT import it either — its test
    stubs `./LyricAppDocument` as `class {}` in node env and would die pulling in
    `appProvider` (see [[appprovider-mock-node-env]]).
  - `stageStyle` is a **getter**, not a field: `stage` is a base-class field that
    `LyricAppDocumentStage1` overrides, and derived fields initialise after the
    base's, so a field initialiser would freeze every stage on stage 0's style.
    More load-bearing since `getStageInstance` STAMPS `stage` after construction
    — anything reading `this.stage` during construction now reads the layout's
    default rather than the stage the caller asked for.
  - The parse memo (`parsedByStage`) was documented as bounded by the two stage
    classes. It is LRU-bounded at 16 entries instead, since the number of stages
    a user can create is now open-ended.
  - The custom CSS is **appended** by `withCustomCss()`, never merged into either
    side of the `allOpenLyricOptions` spread — `css` is a plain string, so the
    last object to carry it wins outright and stage 0 would lose the rules that
    hide its chords. It returns the same object when blank so `genCacheKey` is
    unchanged for untouched installs. Cache invalidation is automatic: every knob
    lands in the hashed options.
  The key is deliberately **unprefixed** (no `getSettingPrefix()`) so presenter,
  reader and screen resolve one key — same reason as
  `open-lyric-previewer-setting`; a divergent key is the SC-08 bug class.
- **Stage resolution used to happen only in the presenter — FIXED 2026-08-03.**
  Two bugs, one root cause (the presented slide is derived for one specific stage
  and nothing re-derived it), both found by robot runs 20260803-1030/-1151:
  a `St: 1` screen projected the stage-0 layout (no chords, no section labels)
  while its own mini-preview looked correct; and changing a screen's `St:` stage
  updated the label but re-rendered *neither* side. Fixes:
  - `getTargetLyricSlideItemData` (`lyricSlideScreenHelpers.ts`) no longer bails
    out on `appProvider.isPageScreen`. It now short-circuits on the cheap,
    import-free conditions instead (`typeof stage !== 'number'`, or the data is
    already on the wanted stage), so ordinary documents and the steady state stay
    free while the screen can repair a wrong-stage snapshot.
  - `ScreenManager.set stage` calls the new
    `ScreenVaryAppDocumentManager.reapplyForStage()` when the value actually
    changes, which re-runs the current slide through the stage-aware setter
    (re-derive → render → persist → sync).
  Keep both halves: the setter alone leaves a cold restore wrong, and the screen
  fix alone leaves stage switching inert. Note the presented slide is otherwise
  an intentional snapshot — a *saved edit* still only reaches the screen on
  re-present (see the XW rows), and that is by design.
- **`metadata.uuid` on lyric slides is dead data** — `Slide.uuid` is a getter
  derived from `filePath` + `id`, and the schema only declares `width`/`height`.
- The rendered HTML carries a **full computed-style dump per node** (~464 KB for
  one chorus slide). That comes from `open-lyric`, not this repo — see
  [[open-lyric-subtree-branch-dep]] for how to change that dependency.

Every other document kind has stages too, drawn at render time instead of
rewriting slides; the Stage Previewer header is shared
(`StagePreviewerHeaderComp`) -- see [[document-stage-previewer]]. Since
2026-10-06 the look-ahead stages (2-5) draw the coming verse at full opacity and
lay their boxes over the whole slide (`displayDim`), not inside
`canvasItemBounds`, so there is no margin around them.
